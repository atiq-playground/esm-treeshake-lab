title: Why ESM wins
description: Singleton registry vs selective ESM imports

## The two arms

**Singleton:** each service module registers itself on import (`registerPublicService`). A plugins index imports **all N** packages, then `registerPublicServices(cfg)` configures whatever is in the registry. Even if the app only **calls** a few `used()` methods, the bundle still paid for every imported plugin (and typically keeps unused class methods / ballast).

**ESM:** import only what you call. Unused packages and unused exports stay out of the graph and are shaken away.

## Call sites (important)

`--fns` is the **surface** per package (how many functions each stub *defines*). It is **not** how many ESM imports by default.

| Case | Surface | What ESM actually calls |
|------|---------|-------------------------|
| UC1 baseline / UC2 wide / UC3 cycles | `N × fns` | **1**: `used` from svc-0 only |
| UC4 partial | `N × fns` | **`--used=K`** (default `⌊N/2⌋`): `used` on K packages; both arms call the same K |

So if someone “only needed 8 functions,” run:

```bash
bun run lab:bench:partial -- --n=100 --fns=40 --used=8
```

Same 8 call sites on both arms; singleton still registers all 100 packages.

## Why the improvement is good (in general)

Smaller bundles mean less to download, parse, and retain in memory: especially on Workers / edge where cold start and isolate size matter. Tree-shaking unused exports is how you keep a large *library* surface without forcing every consumer to pay for it.

Reports compare percentages, not only raw bytes:

- **Bytes saved vs singleton**: primary win (often ~99%+)
- **ESM as % of singleton**: how small the selective graph is
- **Singleton / ESM**: size factor (e.g. hundreds of ×)
- **Call-site coverage**: how much of the defined surface you actually invoke
- **Unused markers removed**: ballast / dead exports dropped

## GraphQL (or any façade) over 100 packages

Imagine a GraphQL service that *can* reach all 100 domain packages (schema stitching, a mega-`resolvers` map, or a plugin registry). At runtime a given deployment or request path might only need **some** of those functions: say half the packages’ entrypoints, or eight mutations.

| Packaging | What gets into the Worker bundle |
|-----------|----------------------------------|
| Singleton registry | Side-effect import of all 100 packages → you ship unused methods and ballast even if GraphQL only wires 50 resolvers |
| ESM selective imports | Import only the resolver implementations you register → pay for those call sites; the other packages/exports stay out |

UC4 (`lab:bench:partial`) is that story: **same K call sites on both arms**, full N still registered on the singleton side. The % saved is the cost of “import everything so GraphQL *could* use it” versus “import what the schema actually binds.”

That does **not** mean GraphQL cannot expose a large schema: it means the **module graph** should follow the resolvers you ship, not a global registry of every package.

## What we measure

esbuild bundles both fixtures and reports **bytes**, **unused markers retained**, **build wall time**, and the percentage comparison table above. Home metrics stay on UC1 (`docs/lab/benchmark-latest.*`); variants write sibling reports.
