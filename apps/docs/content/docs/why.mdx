---
title: Why ESM wins
description: Registry pulls every function; ESM only pays for call sites
---

## In one breath

**Singleton registry:** import the plugins index → every package loads → every function in those packages is in the graph. Cycles pull neighbors too. Bundlers cannot shake it: the side-effect import made it all “live.”

**ESM:** import the functions you call. Everything else stays out.

Same API surface either way. Different bill.

## Why that bill hurts

| Pressure | What happens |
|----------|----------------|
| Depth | Not “N plugins”: N packages × every export / method / ballast inside |
| Cycles | One import can drag a ring of packages you never call |
| No DCE | Side-effect registration defeats tree-shaking; unused code stays |
| Many consumers | Each app that touches the registry pays the full graph again |
| Façades (GraphQL, etc.) | Schema *could* reach 100+ packages; you still only wire some resolvers. Registry ships all of them anyway |

Cold start, isolate size, and deploy bytes follow the module graph, not the resolvers you actually registered.

## The two arms (this lab)

**Singleton:** each service registers on import (`registerPublicService`). A plugins index imports **all N** packages, then `registerPublicServices(cfg)` configures the registry. Even if the app only **calls** a few `used()` methods, you already paid for every plugin’s full surface.

**ESM:** import only what you call. Unused packages and unused exports stay out of the graph and are shaken away.

## Call sites (important)

`--fns` is the **surface** per package (how many functions each stub *defines*). `--used=K` is how many resolvers the schema **binds** (same K on both arms).

| Case | Surface | What both arms call |
|------|---------|---------------------|
| UC1–UC3 (lab default) | `N × fns` | **1** unless you pass `--used=K` |
| Landing lean | `N × 2` | **`--used=200`** (~2/pkg) |
| Landing fat / cycles | `N × 20` | **`--used=300`** (~3/pkg) |
| Landing many | `N × 20` | **`--used=500`** (~5/pkg) |

```bash
bun run lab:bench:wide -- --n=100 --used=300
bun run lab:bench:partial -- --n=100 --used=500
```

Same K call sites on both arms; singleton still registers all 100 packages (and keeps their unused exports).

## What the numbers mean

Reports compare percentages, not only raw bytes:

- **Bytes saved vs singleton**: primary win (often ~99%+)
- **ESM as % of singleton**: how small the selective graph is
- **Singleton / ESM**: size factor (e.g. hundreds of ×)
- **Call-site coverage**: how much of the defined surface you actually invoke
- **Unused markers removed**: ballast / dead exports dropped

## GraphQL over 100 domain packages

This is **not** “do you have 100 random npm dependencies?” It is a GraphQL (or similar) service whose resolver map *can* reach ~100 **first-party domain packages** — stitching, a mega-`resolvers` map, or a plugin registry.

**1 function ≈ 1 field resolver.** If you import 100 domain packages, you typically bind **~2–5 resolvers per package** (not 20 total). Each package may still *define* ~20 exports; the singleton registry ships those unused ones, ESM does not.

| Packaging | What gets into the Worker bundle |
|-----------|----------------------------------|
| Singleton registry | Side-effect import of all 100 → every function in each package stays; unused exports still ship |
| ESM selective imports | Import only the resolver implementations you register → pay for ~2–5 fns/package |

Landing benches: **~2/pkg** (lean), **~3/pkg** (fat/cycles), **~5/pkg** (many) — same K on both arms; singleton still registers all N.

**Out of scope (important):** these stubs do **not** include `graphql`, DataLoader, ORMs, auth SDKs, or other third-party deps. Real services pull those too; they can grow the bundle far more. The numbers isolate the **first-party module graph** cost of “import everything so GraphQL *could* use it” versus “import what the schema actually binds.”

Large schemas are fine. A global registry of every domain package is not how the **module graph** should look.

## What we measure

esbuild bundles both fixtures and reports **bytes**, **unused markers retained**, **build wall time**, and the percentage comparison table above. Home metrics stay on UC1 (`docs/lab/benchmark-latest.*`); variants write sibling reports.
